Flyover · Rootstock

Removing the liquidity‑DoS with a commit‑first peg‑in

Flyover's off-chain quote negotiation is replaced by a user-commits-first model: the user makes the on-chain commitment first, then liquidity providers detect it and compete to serve it. No LP liquidity is reserved before the user commits — which removes the denial-of-service vector at its root.

Full cycle proven on a live regtest (rskj 9.0.2) — no bridge changes required

The problem

In the legacy model the user requests a quote and accepts it off-chain; at that moment the LP reserves liquidity for a ~1 hour window before any on-chain payment exists. An attacker accepts genuine, LP-signed quotes and never funds them, locking liquidity for the full window at zero cost, and repeats — keeping an LP dark indefinitely. The same per-quote design also blocks institutions: the deposit address is single-use (nothing stable to whitelist) and the acceptance window expires during multi-hour multisig signing.

The model

Commit first

The user sends BTC to a deterministic address derived from their RSK address. No quote, no acceptance.

LPs compete

LPs detect the on-chain commitment and race to serve it. The first to claim wins; the rest revert cheaply.

Nothing reserved

No liquidity is held before the user commits — so there is nothing for an attacker to spam.

New & changed contracts (liquidity-bridge-contract, Foundry)

Contract Role
FlyoverConfigurations new Economics on-chain: fixed-floor + percentage fee, amount-keyed confirmation tiers, deadlines and limits. Setters are time-locked with immutable deployment bounds.
PegInAddressRegistry new Derives the deterministic deposit address from the RSK address; records registrations (permissionless, read-only SPV deposit-gated); keeps a running hash registrationRoot for watch-list integrity. Emits AddressRegistered.
PegInContract reworked requestPegIn (LP fronts RBTC from its own wallet against a full SPV proof) and resolvePegIn (settles with the bridge to reimburse the LP). OP_RETURN carries optional contract-call data; first-mined claim wins.
CollateralManagement extended Adds a proportional global slash across all registered LPs when nobody serves a valid peg-in, plus a no-penalty grace window after registration; keeps the per-LP individual slash.

Server & client

  • liquidity-provider-server (Go) — a new event-driven discovery watcher (watch AddressRegistered, monitor Bitcoin for deposits), a competitive claim path, and the removal of the off-chain accept-time reservation that was the DoS surface.
  • flyover-sdk + bridges-core-sdk (TypeScript) — the client reads the deposit address from the registry and fees from configuration, and builds the BTC transaction (optional OP_RETURN) instead of negotiating a quote. The registry is the single source of truth for the address, so SDK and LPS never re-implement derivation.

How a peg-in works

A real ordered sequence — each step names who acts.

  1. 1
    SDK · view

    Derive the deposit address. The client calls getPegInAddress(rskAddr), which derives a deterministic P2SH against the live powpeg redeem script. Stable across calls; changes only on a federation change.

  2. 2
    User · Bitcoin

    Commit BTC. The user sends BTC to that address (optionally an OP_RETURN output destContract ‖ maxGas ‖ callData for a smart-contract peg-in). The only user action — no quote, no acceptance, no reservation.

  3. 3
    Watchtower / user · on-chain

    Register the address. Once the deposit confirms, registerAddress records it, gated by a read-only SPV proof: the contract parses the BTC tx outputs to confirm one pays the derived address and checks confirmations via the bridge's view method — without consuming the peg-in.

  4. 4
    LPS · discovery

    Discover & watch. LPs watch AddressRegistered (verified against registrationRoot) and monitor Bitcoin for a confirmed deposit to each registered address.

  5. 5
    LP · requestPegIn

    Claim and front RBTC. The first LP calls requestPegIn with the full SPV proof, validates the deposit and confirmations, and forwards RBTC from its own wallet to the user (amount − fee) — or to the OP_RETURN destination. Competing LPs revert cheaply.

  6. 6
    LP · resolvePegIn

    Settle & get reimbursed. The LP calls resolvePegIn, which invokes the bridge's one-shot registerFastBridgeBtcTransaction with the SPV proof; the bridge releases the pegged funds to the LBC, reimbursing the LP plus the fee.

If no LP claims a valid peg-in by the deadline (anchored to the registration block), the network takes a global slash — so every LP is incentivized to ensure someone serves it.

Key design decisions

Decision Why
Commit-first, no off-chain reservationThe only way to satisfy "no liquidity reserved before the user commits comparable capital" — closes the DoS structurally.
Deterministic address from the RSK addressStable, whitelist-once for institutions; not tied to any LP, so any LP can serve it.
Read-only SPV deposit-gatingThe bridge's settlement call is one-shot — registration must validate the deposit without consuming it, or the LP's claim would fail.
Full SPV proof in the claimThe rskj bridge has no by-hash confirmation lookup; a hash-only check always fails against a real node.
Bridge-compatible derivation, fixed placeholdersSo the address the user pays matches what the unmodified bridge re-derives at settlement; fixed placeholder refund/LP values keep it LP-agnostic.
Global slash + grace window; time-locked configIncentivize serving every peg-in without punishing freshly-onboarded LPs; prevent economics changing mid-operation.

Open item

Failure-refund placeholder

Because the deposit-address derivation uses fixed placeholder refund/LP BTC addresses (to stay LP-agnostic while matching the bridge), the bridge's failure-refund branch would send funds to the REFUND_PLACEHOLDER address. It must be a single protocol-owned, monitored BTC address (never empty). The branch should be unreachable given the pre-front validity and minimum-amount checks, but it is an operational requirement before production.
